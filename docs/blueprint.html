Production Blueprint

QrDine — the build plan before the build

A restaurant QR-ordering platform for the Pakistan market: scan a table, order, and watch it move through reception, kitchen timing, waiter service and billing — live. This document is the architecture, the flows, and the exact file layout, agreed before a line of production code is written.

Backend · ASP.NET Core 9 · Clean Architecture Realtime · SignalR Data · PostgreSQL · EF Core Frontend · React (Vite) PWA Model · Multi-tenant · feature-flag modules
01System context

Who talks to what

Five surfaces share one backend. Customers use their own phones (no install); staff use cheap Android tablets or any browser. The API is the single source of truth; SignalR pushes every change out so no screen ever needs a manual refresh.

02Clean architecture

Four layers, one rule: dependencies point inward

The demo put everything in Program.cs — fine to prove the idea, wrong to sell. Production splits into four projects. The Domain at the centre knows nothing about databases, HTTP or SignalR, so business rules are testable in isolation and survive any change of framework. Everything on the outside depends on the inside, never the reverse.

Domain

The rules, framework-free

Entities and aggregates (Order, TableSession), enums, domain events, invariants. The Order aggregate owns its own transitions — an invalid Placed → Served throws here, not in a controller.

Application

The use cases

One class per action — PlaceOrderCommand, StartCookingCommand, GetStaffOrdersQuery — with validation and orchestration. Depends only on Domain and its own interfaces.

Infrastructure

The outside world

EF Core DbContext + migrations, repositories, the SignalR notifier, JWT, and the payment / FBR / WhatsApp / printer clients. All behind interfaces.

Api

The thin edge

Endpoints, hubs, middleware (tenant resolution, auth, error handling), and DI wiring. Translates HTTP into a use-case call and returns the result. No business logic lives here.

03Order lifecycle

One order, six states, guarded transitions

This state machine is the heart of the product. Each arrow is triggered by exactly one role and is only legal from the state before it — the Order aggregate rejects anything else. That is what stops a waiter marking food "served" before the kitchen ever cooked it.

04End-to-end flow

The flows to pass

Read top to bottom: this is one table's journey through the system. Each horizontal arrow is a real API call or a real live push. If every one of these passes, the core product works.

Edge: out of stock

Kitchen toggles an item unavailable → it greys out on every open phone instantly; in-cart items are flagged before checkout.

Edge: guest can't scan

Waiter places the identical order from the waiter app on behalf of the table — same pipeline, same kitchen ticket.

Edge: connection drop

Screens re-fetch open orders on reconnect and re-join their SignalR group, so a blip never loses an order.

05Data model

Multi-tenant from row one

Every tenant-owned row carries RestaurantId, and an EF Core global query filter scopes every query to the current tenant automatically — one database safely serves every restaurant. Below: the core aggregates shipping first, and what hangs off them later.

Tenant & access
  • Restaurant — tenant root, currency, feature flags
  • Branch — a location under a restaurant
  • StaffMember — login + Role (owner/manager/cashier/kitchen/waiter)
  • DiningTable — code + name, carries the QR
Menu
  • MenuCategory — ordered sections
  • MenuItem — name (EN/UR), price, photo, prep-minutes, availability
  • MenuItemVariant — half / full, small / large
  • ModifierGroup / Modifier — spice level, add-ons, "no onion"
Ordering (the spine)
  • TableSession — opens on first scan, closes at payment
  • Order — aggregate root; status, ETA, waiter, timestamps
  • OrderItem — line, qty, note, chosen variant
  • OrderItemModifier — the picked add-ons
Billing & beyond (later)
  • Payment — method, amount, tip
  • Invoice — tax lines, FBR/PRA number + fiscal QR
  • StockItem / RecipeLine — inventory & costing
  • AuditEvent — voids, discounts, comps (theft control)
Why TableSession matters.

Without it, a fresh customer scanning the QR sees the previous diner's orders and bill. The session is the boundary between one seating and the next — it is the single most important thing the demo is missing, and it goes in first.

06Modules & pricing

Sold as feature flags, not forks

One codebase, one deployment. Each restaurant's Restaurant.Features switch turns modules on; the UI hides what isn't licensed. You start owners cheap on the QR menu and upsell the operations layer — the part they can't get elsewhere.

M0 · QR Menu

The cheap yes

Table QR, digital menu (EN/UR), photos, availability, "call waiter". No ordering. Foot in the door.

M1 · Ordering

Self-order + tracking

Table sessions, cart, order placement, live status + ETA countdown, "order more".

M2 · Operations

Where the money is

Reception, KDS with timing, waiter app, table map, receipts. The time-saving system owners lack.

M3 · Billing & tax

Compliance lever

Full billing, split/merge, discounts, GST, and FBR/PRA/SRB fiscal invoicing.

M4 · Business

Owner cockpit

Inventory, recipe costing, multi-branch, staff roles, sales/theft analytics.

M5 · Integrations

Reach

Payments (JazzCash/Easypaisa/Raast), WhatsApp receipts, Foodpanda, loyalty, reservations.

08Demo → production

The changes to make, in order

The demo proves the flow; these are the concrete edits that turn it into software you can charge for. Each is independently shippable — we do them top-down.

01
Split into four projects. Lift the demo's logic out of Program.cs into Domain / Application / Infrastructure / Api. The state machine moves into the Order aggregate.
02
Swap in PostgreSQL. Replace UseInMemoryDatabase with UseNpgsql, add the initial EF migration, move seed into DemoSeeder.
03
Real tenancy. Resolve the tenant from a subdomain/JWT claim in middleware and apply an EF global query filter — stop trusting the slug in the URL.
04
Auth & roles. JWT for staff with role-gated endpoints; short-lived anonymous table-session tokens for guests so only the right table can post.
05
Table sessions. Open on first scan, attach every order, close on payment — the fix for "next guest sees old orders".
06
Validation & errors. FluentValidation on every command; a middleware that returns clean ProblemDetails instead of raw 500s.
07
Variants & modifiers. Half/full, spice level, add-ons — essential for a desi menu and its pricing.
08
Observability. Serilog structured logs, health checks, and a Redis backplane so SignalR scales past one server.
09
Tests + CI. Unit-test the state machine, integration-test the whole flow on a throwaway Postgres, wire a GitHub Actions pipeline.
10
Package & deploy. Docker Compose (api + postgres + redis + nginx) on a cheap VPS, Cloudflare in front, object storage for menu photos.
09Build roadmap

What we build, in what order

Phases 1–3 are buildable end to end right now. Phases 4–5 depend on third-party access (fiscal APIs, payment merchant accounts, aggregator partnership) — we design the seams now and slot the providers in when credentials arrive.

Recommended first move.

Build P1 as the clean-architecture skeleton and port the working demo flow into it — same behaviour you already saw, but on the production foundation. That gives you something correct to grow, and something real to show owners while the rest lands module by module.
